Typed Async Job Queue with Retry & Concurrency Control

You're building the background job runner for a SaaS platform. Jobs arrive with varying priorities and retry budgets, must be executed with a bounded concurrency limit, and each outcome — success, failure, or exhausted retries — must be captured in a fully typed result record that downstream consumers can pattern-match exhaustively.

Goals

  • Define a branded `JobId` type and a generic `Job<T>` interface so the compiler rejects raw strings and untyped payloads.
  • Implement `runJob<T>` with correct retry logic that returns the right discriminated-union variant (`succeeded`, `failed`, or `exhausted`) based on attempt count and outcome.
  • Implement `runQueue<T>` that enforces a concurrency cap, sorts by priority (high → normal → low), and returns outcomes in the original input order.
  • Implement `summariseOutcomes<T>` that exhaustively pattern-matches every `JobOutcome` variant to produce a fully typed `QueueSummary`.
challenge.ts 
// Key types at a glance

export type JobId = string & { readonly __brand: "JobId" };

export interface Job<T> {
  id: JobId;
  priority: "high" | "normal" | "low";
  maxRetries: number;
  payload: T;
  execute: (payload: T) => Promise<T>;
}

export type JobOutcome<T> =
  | { status: "succeeded"; jobId: JobId; result: T;    attempts: number }
  | { status: "failed";    jobId: JobId; error: string; attempts: number }
  | { status: "exhausted"; jobId: JobId; error: string; totalAttempts: number };

// ---- Functions you must implement -------------------------

export function makeJobId(raw: string): JobId { ... }

export async function runJob<T>(job: Job<T>): Promise<JobOutcome<T>> { ... }

export async function runQueue<T>(
  jobs: Job<T>[],
  concurrency: number
): Promise<JobOutcome<T>[]> { ... }

export function summariseOutcomes<T>(outcomes: JobOutcome<T>[]): QueueSummary { ... }

Hints

  • For bounded concurrency without a library, maintain an active-count counter and a Promise chain — or use a pool of `concurrency` worker loops that each pull from a shared index.
  • Branded types require only a type-level intersection (`string & { readonly __brand: 'JobId' }`); the factory just casts internally — but resist using `as` anywhere in the stubs themselves.
  • When narrowing `JobOutcome<T>` in `summariseOutcomes`, switch on `outcome.status` — TypeScript will enforce exhaustiveness if you add a `default: never` guard.
